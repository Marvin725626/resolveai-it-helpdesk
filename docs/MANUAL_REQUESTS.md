# 主动报障与处理闭环

用户可在“我的报障”直接描述问题，不必先运行 AI 诊断。主动报障和 AI 转人工进入同一个工作区处理队列，但保留真实来源。

## 提交与跟进

1. 打开“我的报障”，新建报障，填写标题、问题类别和详细描述。说明故障现象、影响范围以及已尝试的步骤；不要填写密码、令牌或验证码。
2. 提交后查看自己的工单详情。初始状态为待处理，优先级为中；工程师可根据实际影响进行分诊。
3. 按需上传现有支持格式内的截图或日志，发送公开补充信息；附件仍按工单访问权限保护。
4. 工程师接手、公开回复和解决问题后，报障人可以确认解决并为本轮解决记录评分；问题仍存在时可按既有流程反馈。

主动报障不执行模型调用、检索或诊断工具，不生成虚构 AI 回答或诊断运行记录。诊断统计仍仅计入实际运行。

## API

`POST /api/v1/helpdesk/my-tickets` 接受 `request_id`（UUID）、`subject`（清理后4–200字符）、`description`（清理后10–4000字符）与 `category`（network/account/software/hardware/other，默认other）。成功返回 `ticket_id` 与 `cached`。未知字段会被拒绝；客户端不能提交 `tenant_id`、`user_id`、`customer_id`、`priority` 或 `status`。

`GET /api/v1/helpdesk/my-tickets` 统一列出本人的两种来源工单；`GET /api/v1/helpdesk/my-tickets/{id}` 展示本人的手动提交内容，AI 工单保持原有公开详情边界。支持人员仍使用现有 `/helpdesk/tickets` 工作流。

## 所有权与重试

手动提交记录关联当前登录用户、工作区和工单。请求不能指定其他报障人、工作区或接手人员，也不能直接设置状态或紧急程度。旧 AI 转人工工单继续通过原有运行记录识别报障人。

提交带唯一请求 ID；相同请求和相同规范化内容的重试返回同一工单，不重复创建。重试时保留原请求 ID，修改内容后使用新请求 ID。其他用户不能通过复用 ID 读取工单。正文经过现有输入处理与凭据模式脱敏，但脱敏不代替用户检查提交内容。

公开跟进、附件、确认与评分复用现有权限及版本冲突处理。通知使用固定摘要，不把问题正文或私有附件内容写入通知。

## 数据升级与验证

新增独立提交记录表和 Alembic 迁移；不通过伪造 AI 运行保存所有权。Docker 启动会执行迁移，本地 SQLite 开发模式按既有 bootstrap 创建缺失表，不删除旧工单或旧运行。

本批45项隔离回归、PostgreSQL同请求并发、浏览器闭环、容器重建与恢复后所有权验证均通过。具体结果见[验证记录](VALIDATION.md)。部署、备份和恢复说明见[DEPLOYMENT.md](DEPLOYMENT.md)。
