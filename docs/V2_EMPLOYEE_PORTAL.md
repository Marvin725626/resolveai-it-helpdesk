# ResolveAI 2.0：员工门户与服务目录

2.0 将员工提交请求、管理员维护服务、工程师协作处理连成同一条流程。

| 角色 | 使用范围 |
| --- | --- |
| 员工 REQUESTER | 已发布服务、本人报障、公开回复、私有附件、确认解决、满意度和个人通知 |
| 支持专员 SUPPORT_AGENT | 原有诊断与支持工作台、队列、工程师处理；可查看已发布服务 |
| 工作区所有者/管理员 | 支持工作台、人员邀请、服务目录维护、发布、归档及版本历史 |

旧用户角色保持原样。旧邀请以及未指定角色的 API 邀请仍为支持专员；新增员工需管理员明确选择员工角色。链接由管理员手动分享，不自动投递邮件。

## 员工使用流程

1. 接受管理员创建的员工邀请，登录后进入服务大厅。
2. 查看本人的待处理、待确认和已关闭请求；从已发布的服务中选择需要的事项。
3. 按表单填写必填信息。服务可使用短文本、长文本或选择项；不要填密码、验证码和令牌。
4. 提交后进入自己的工单，继续补充公开信息、上传截图或日志。
5. 收到回复或处理进度通知后打开本人详情；工程师解决后确认关闭，并可为该轮处理评分。

非标准故障可继续使用通用主动报障。服务申请只创建待处理工单；实际账号授权、软件部署等操作仍由支持人员按自己的流程核实和处理。

## 服务目录维护

管理员可以新建服务、编辑最多六个字段、预览表单，再选择发布。员工只能读取本工作区已发布服务；草稿和归档服务不在员工目录展示。

编辑、发布和归档都检查版本，防止两个管理操作相互覆盖。目录修订保留当时的内容及操作人；已提交工单保存服务名称、模板版本、字段标签和答案快照。后续修改或归档服务不会改写原申请。

提交失败且结果不确定时可以重试原提交；同一请求不会重复建单。改变答案或服务版本后提交新的请求。服务表单已更新时会要求重新加载，保留输入供用户核对。

## 权限与数据边界

员工导航只有服务大厅、我的报障与个人通知。服务端还对 REQUESTER 的方法与路由进行默认拒绝，只开放明确的个人及目录操作；不能通过手工请求支持队列、团队指标、知识维护、配置和旧后台接口读取同事资料。

本人工单、公开附件和通知沿用工作区与用户归属检查；内部备注不向员工公开。员工门户统计也只来自本人的请求。现有智能诊断仍由支持工作台使用，未向员工公开内部知识库。

## 升级与运行

两项新增迁移依次增加员工角色/邀请目标角色，以及服务目录和修订表。已有账号和工单保留；旧邀请默认支持专员。PostgreSQL 需要扩展原生角色枚举，SQLite 需要新增邀请角色列；不能仅替换前端或跳过数据库迁移。

Docker 使用原有 `scripts/docker_deploy.py up`，启动时执行 Alembic。Windows 开发入口 `start.ps1` 在启动应用前执行迁移。升级前保留数据库和附件备份，具体命令见[部署说明](DEPLOYMENT.md)与[运维说明](OPERATIONS.md)。已有员工数据时禁止直接降级回不能识别员工角色的旧版本。

实测范围与结果见[验证记录](VALIDATION.md)。本地演示使用合成账号和请求，不代表真实企业资源开通、SSO、邮件或真实模型验收。
